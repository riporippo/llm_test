# 連続稼働試験（2026-11-10 夜）と Qwen3.5-397B 試用の分析

データ：`bench/soak_soak-gpt-oss-20b-head_20261110-2248.csv`、`bench/soak_test_20261110-2244.csv`、`bench/gpu_log.csv`、`chat_log.jsonl`

## 1. 結論

- **8時間試験は、開始21分後（23:09）に llama-server が応答しなくなり、実質21分で終わっていた。** 残りの約8時間は接続拒否のエラーが 10,616 件記録されただけ。
- 止まるまでの21分間の性能は良好。**4人同時でも、1人あたりの生成速度は中央値 39 tok/s、応答時間は中央値 11 秒**（95パーセンタイルで 26 秒）。判定基準の 5 tok/s を大きく超える。
- GPU の温度は最高 75℃、消費電力は最大約 87W（A4000 の上限は 140W）、クロックは 1560 MHz で安定していた。**熱による速度低下は起きていない。** 停止の原因は熱ではない。
- 停止の原因は、記録が足りず特定できない。**次回は llama-server の出力をファイルに残す**（§4）。
- Qwen3.5-397B-A17B（UD-IQ3_XXS）は**生成 3.9 tok/s で △**。計画の見込みどおりだった。それより問題なのは入力処理が **9〜12 tok/s と極端に遅い**こと（§3）。

## 2. gpt-oss-20b（ヘッド、4人同時）

### 2.1 何が起きたか（時系列）

| 時刻 | 出来事 | 根拠 |
|---|---|---|
| 22:44 | 2分間の試験運転。20件すべて成功 | soak_test |
| 22:48 | 本番開始 | |
| 22:48〜23:09 | 239件すべて成功。エラーなし | soak CSV |
| 23:09 頃 | **応答が止まる。** GPU 使用率が 0%、消費電力が 16W に下がる。VRAM（5.9GB）は確保されたまま | gpu_log 23:10 以降 |
| 23:09〜23:19 | 実行中だった4件が、600秒待っても応答がなくタイムアウト | TimeoutError ×4 |
| 23:19〜23:25 頃 | 次の4件が受け付けられたまま約6分止まり、接続が切られる | RemoteDisconnected ×4 |
| 23:25〜23:43 の間 | **VRAM が 254MB に下がる＝llama-server のプロセスが終了した** | gpu_log |
| 以降 06:48 まで | 接続拒否が続く（soak.py が10秒おきに試し続けた） | Connection refused ×10,616 |

- **まず「固まった」（プロセスは生きていて VRAM も確保したまま、計算だけ止まった）。その約15分後に「終了した」**、という2段階で止まっている。最初から落ちたのではない。
- 終了が、自分で落ちたもの（クラッシュ）なのか、誰かが止めたものなのかは、記録からは区別できない。

### 2.2 止まるまでの性能（239件）

| 項目 | 中央値 | 5％点 | 95％点 |
|---|---|---|---|
| 生成速度（1人あたり） | **38.9 tok/s** | 21.5 | 74.4 |
| 入力処理速度 | 952 tok/s | ―（入力が数トークンだと値が不安定） | 1,439 |
| 応答時間（1件） | **10.7 秒** | 1.2 | 25.6 |
| 生成トークン数 | 482 | 45 | 751 |
| 推論の文字数（effort=low） | 63 字 | 20 | 236 |

- 全体の処理量は約 73 tok/s、11件/分。学生が回答を読む時間（0〜20秒）を挟むので、常に4本が同時に走っているわけではない。
- 生成速度は 5分ごとの中央値で 33〜43 tok/s。21分の間に遅くなる傾向はなかった。
- 一人で走ったときは最大 84 tok/s。同時に走る本数が増えると、1本あたりは 20 tok/s 台まで下がる。
- 終了理由はすべて `stop` で、生成上限（1024）で切れた回答はなかった。`--reasoning-effort low` が効いて、推論は短い。
- 回答の長さを見ると、シナリオ1の3ターン目（「50字以内で」）は中央値 42 字で、指示を守っている。中身の良し悪しは、このログ（文字数だけ）では判断できない。

### 2.3 気になる点

- **VRAM 使用量が 5.9GB しかない。** gpt-oss-20b は重みだけで 12GB あるので、全部が GPU に載っているなら 13GB 前後になるはず。重みの半分程度がメインメモリに置かれていた可能性がある（新しい版の llama.cpp が自動で配分した、など）。起動ログの `offloaded N/M layers to GPU` と、`CUDA0 model buffer size` を確認したい。全部 GPU に載れば、さらに速くなる余地がある。
- 停止の原因の候補（いずれも推測）：
  1. llama.cpp の、複数スロット（`-np 4`）とプロンプトキャッシュの組み合わせの不具合。gpt-oss は一部の層で局所注意（SWA）を使うので、キャッシュの扱いが特殊になる。止まる直前のリクエストは、どれもキャッシュを再利用する2・3ターン目だった。
  2. メインメモリやディスクなど、GPU 以外の資源の問題。
  3. 誰か（または何か）がプロセスを止めた。

  どれなのかは、llama-server の出力が残っていれば確認できた。

## 3. Qwen3.5-397B-A17B（UD-IQ3_XXS、140GB）を対話で試した結果

| 質問 | thinking | 入力 | 入力処理 | 生成 | 最初の出力まで | 合計時間 |
|---|---|---|---|---|---|---|
| あなたの特徴を教えて | オフ | 60 tok | 8.6 tok/s | 290 tok、**3.90 tok/s** | 7.1 秒 | 81 秒 |
| 最適なハーネスは？ | オン | 70 tok | 12.2 tok/s | 2,048 tok（**上限で打ち切り**）、3.85 tok/s | 5.8 秒 | **537 秒** |
| 明日の天気は？ | オン | 58 tok | 11.6 tok/s | 818 tok、3.88 tok/s | 5.0 秒 | 216 秒 |

- **生成は 3.9 tok/s で安定。** 判定は △（5 tok/s 未満）。計画では、Q4 で2台に分けた場合に約5 tok/s と見ていた。今回は 3bit で、ヘッド1台と思われる構成なので、見込みとおおむね合っている。
- **入力処理が 9〜12 tok/s しか出ていない。これが最大の問題。** このままだと、7k トークンの入力の処理だけで約10分かかる。専門家層をメインメモリに置いた構成で、入力の処理を CPU でしているためと考えられる。`-ub 2048 -b 2048` などで大きなバッチにすると、GPU で処理されて速くなる可能性がある（計画 §4 段階1の注意点）。
- **thinking をオンにすると実用にならない。** 推論だけで数百〜2,000 トークンを使い、1問に4〜9分かかる。しかも推論は英語で書かれていた（"Thinking Process: …"）。教育利用では thinking はオフが前提になる。
- 「明日の天気は？」には、リアルタイムの情報は持っていないと断っていて、適切に答えられた。
- ログの4件目は `exit` という文字が質問として送られたもの。chat.py の終了コマンドは `/quit` だった。今回の修正で、`exit`、`quit`、`bye` でも終了するようにした。

## 4. 次に試すとき

1. **llama-server の出力をファイルに残す**（いちばん大事）：
   ```bash
   ./build/bin/llama-server ...（オプションは前回と同じ） 2>&1 | tee ~/llm_test/bench/server_$(date +%Y%m%d-%H%M).log
   ```
2. **起動ログで、層がすべて GPU に載っているかを確認する**（§2.3）。載っていなければ `-ngl 99` を明示するか、`--fit` 系のオプションを確認する。
3. **soak.py を更新した。** 15分間1件も成功しなければ「サーバーが止まった」と表示して打ち切る（`--give-up-min` で分数を変えられる。0 にすると打ち切らない）。最後に成功した時刻も最後に表示する。今回のように、エラーの行だけが8時間たまることはなくなる。
4. 原因を切り分けるには、同じ条件でもう一度回し、止まるかどうかを確かめる。止まった場合は、次の2通りで比べる。
   - `-np 1 --users 1`：1人だけで止まるか
   - `--cache-ram 0 --ctx-checkpoints 0`（パイロットで付けていたオプション）：プロンプトキャッシュをやめると止まらなくなるか
5. 自動で再起動させたい場合は、llama-server を `while true; do ./build/bin/llama-server ...; sleep 5; done` のように包む。ただし、これで助かるのは落ちた場合だけで、固まった場合は再起動されない。まずは原因を見つけるのが先。
