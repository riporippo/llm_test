# 調査2：小型モデルの結果と、合格基準での判定

測定日：2026-11-17（`run_all.py` で自動実行。記録は `bench/logs/run_all_20261117-2012.csv`）
対象：Gemma 4 26B-A4B、LFM2.5-24B-A2B、gpt-oss-20b、Gemma 4 12B、Qwen3.5-9B（11月14日までに測った3モデルも並べて判定）

## 1. 合格基準

| 項目 | 基準 |
|---|---|
| 速度 | 4人同時に使ったとき、1人あたりの生成速度の**最小値**が 10 tok/s 以上 |
| 精度 | 精度の問題（61点満点）で正答率 85% 以上、かつ**誤検知ゼロ**（侵害なしのログを「侵害あり」と判定しない） |
| 両方を満たすモデルがない場合 | 基準に最も近いものを選ぶ |

## 2. 結論

- **両方の基準を満たすモデルは、まだない。**
- **基準に最も近いのは Gemma 4 26B-A4B。** 精度は合格（88.5%、誤検知ゼロ）で、速度の最小値は 9.9 tok/s と、基準まで 0.1 tok/s。この差は測定のばらつきより小さいので、測り直して確かめる。
- 精度が最も高いのは Qwen3.6-35B-A3B と Gemma 4 12B（どちらも 91.8%、誤検知ゼロ）。ただし速度の最小値はどちらも 8.1 tok/s。
- 速度の基準を満たしたのは、活性パラメータが特に小さい LFM2.5（最小 19.0 tok/s）と gpt-oss-20b（最小 15.6 tok/s）。**この2つは精度を正しく測れていない**（3章）ので、測り直す。

## 3. 精度を測り直す必要があるモデル

LFM2.5 と gpt-oss-20b は、どちらも答える前に推論（thinking）を出力するモデル。精度の測定では生成上限を 4,096 トークンにしていたが、**推論だけでこの上限を使い切り、回答を書く前に打ち切られた**。

| モデル | 打ち切られた問題 | 状態 |
|---|---|---|
| LFM2.5-24B-A2B | 7問中7問 | 7問とも回答が空（推論は 1万〜1.4万字）。0/61 点は実力ではない |
| gpt-oss-20b | 7問中5問 | 4問は回答が空。1問は回答の途中で切れた（その1問は本文から 7/11 点） |

- 4人同時の速度の測定（生成上限 1,024）でも、LFM2.5 は12件すべてが推論の途中で打ち切られ、回答が空だった。生成速度（tok/s）は有効だが、「回答が出るまでの時間」は測れていない。
- gpt-oss-20b は、打ち切られずに答えた侵害なしのログ1本で「侵害あり」と判定している（攻撃元として、無差別な総当たりの 192.0.2.x を挙げた）。測り直しても、この誤検知が残れば精度は不合格になる。
- 測り直しの設定は `models.json` に入れた（生成上限：精度 12,288、LFM2.5 の4人同時 8,192。文脈もそれに合わせて広げた）。

## 5. わかったこと

1. **密なモデルは、小さくしても速くならない。** Gemma 4 12B と Qwen3.5-9B は、容量は 5.7〜7.1GB と小さいが、1人での生成は 35〜48 tok/s で、MoE の Qwen3.6（67 tok/s）や gpt-oss-20b（80 tok/s）より遅い。4人同時の最小値も 5.4〜8.1 tok/s で、基準に届かなかった。MoE は1トークンごとに一部の専門家しか計算しないので、総パラメータが大きくても速い。
2. **4人同時で速いのは、活性パラメータが特に小さい MoE。** LFM2.5（活性 2.45B）と gpt-oss-20b（活性 3.6B）は、4人同時でも最小値が 15〜19 tok/s。Gemma 4 26B-A4B（活性 3.8B）と Qwen3.6（活性 3B）はその次。
3. **この課題の精度は、モデルの大きさにあまり左右されない。** Gemma 4 12B（密 12B）が、Qwen3.6（36B）と同じ 91.8%。どのモデルも、失点の大半は UNIX 時刻の日本時間への換算（gpt-oss-120b 以外は全問不正解）。
4. **誤検知の出方はモデルによって違う。** GLM-4.7、Qwen3.5-9B、gpt-oss-20b は、侵害なしのログで、無差別な総当たり（192.0.2.x）や社内からの正規のログインを攻撃と判定した。Gemma 4 26B-A4B も、侵害なしと判定しながら総当たりの IP を「攻撃元」の欄に書いた回と、侵害の有無を「不明」とした回があった（採点では誤検知に数えていない）。
5. **推論するモデルは、回答までが長い。** LFM2.5 は1問 73 秒かけても回答に届かなかった（推論だけで 4,096 トークン）。エージェントとして何度も呼ぶ使い方では、この長さが手数ごとに積み重なる。

## 6. 次にやること

コマンドは Head の `~/llm_test/bench` で実行する。準備（Worker のスリープ停止、rpc-server の起動、tmux）は `docs/手順書_次の調査_20261117.md` の 0章のとおり。

### 6-1. LFM2.5 と gpt-oss-20b を測り直す（約1時間）
```bash
python3 run_all.py --only lfm2.5-24b-a2b --phases quiz,speed4 --force
```
```bash
python3 run_all.py --only gpt-oss-20b --phases quiz --force
```
`--force` で測った結果は、同じ条件の古い結果と置き換わる（`report.py` は新しいほうで集計する）。起動コマンドに `-c` や `--max-tokens` が2回出てくるが、後ろの値が使われる。

### 6-2. Gemma 4 26B-A4B と Qwen3.6 の4人同時の速度を、もう一度測る（約20分）
9.9 tok/s と基準の差は、測定のばらつきより小さい。同じ条件でもう1セット測り、最小値が安定しているかを見る。別の名前で記録するので、1回目の結果は残る。
```bash
~/llama.cpp/build/bin/llama-server -hf unsloth/gemma-4-26B-A4B-it-GGUF:UD-Q4_K_M --no-mmproj -ngl 99 --rpc 172.18.1.57:50052 --ctx-checkpoints 0 --cache-ram 0 -c 32768 -np 4 --host 127.0.0.1 --port 8080
```
別の窓で：
```bash
python3 audit_bench.py out_audit/audit.log --parallel 4 --runs 3 --label research2-gemma4-26b-a4b-2nd
```
Qwen3.6 も同じように（`-hf unsloth/Qwen3.6-35B-A3B-GGUF:UD-Q4_K_M`、label は `research2-qwen3.6b-2nd`）。

### 6-3. RPC あり・なしの対照実験（手順書の 3章）
- Gemma 4 26B-A4B（16.9GB）は、Worker の GPU（20GB）1台に載る。手順書の構成 C（GPU ごとに別々のサーバー）を、gpt-oss-20b に加えて Gemma 4 26B-A4B でも試す価値がある。ただし Head の GPU（16GB）には載らないので、Head 側は別のモデルか、構成 B は省く。

### 6-4. エージェントとしての測定（手順書の 5章）

6-1 の測り直しで LFM2.5 と gpt-oss-20b の精度が合格したら、`--only` に足す。
