# 研究メモ：4人同時利用時の遅延の原因（llama.cpp の構成比較）

作成：2026-11-19（前回の研究メモ「現構成 GPU クラスタの動作可能モデルに関する研究メモ」とは別の記録）

## 1 はじめに

前回の調査（調査1・2）で，llama.cpp の分散推論（RPC）で2台の GPU を束ねた現構成では，4人が同時に使うと応答時間が単独時の3〜4倍になり，1人あたりの生成速度の最小値がほとんどのモデルで 10 tok/s を下回った．この遅さの原因として，次の2つが考えられたが，前回のデータでは区別できなかった．

- RPC で層を2台に分けていること
- 4人で GPU を分け合うこと

そこで，同じモデルを3通りの構成で動かし，4人同時の速度を比べた．

## 2 実験方法

### 2.1 比べた構成

| 構成 | 内容 |
|---|---|
| A | RPC で2台の GPU に層を分ける（現構成） |
| B | Head の GPU（RTX A4000）1台だけで4人を受ける |
| C | GPU ごとに別々のサーバーを立て，2人ずつ受ける．Head の GPU のサーバーと，Worker の GPU を RPC 経由で使うサーバー（層は分けない）の2つ |

### 2.2 条件

- モデル：gpt-oss-20b（`ggml-org/gpt-oss-20b-GGUF`，MXFP4，12.1GB）．どちらの GPU にも1台で載る．
- 課題：前回と同じ架空の auditd ログ（5,707 トークン）の要約を，4人同時に3セット（計12件）．temperature 0.7，生成上限 1,024 トークン．
- キャッシュは無効（`--ctx-checkpoints 0 --cache-ram 0`）．
- 速度は，応答をストリーミングで受けながら手元で計測した（`audit_bench.py --client-timing`）．
  - 最初の出力まで：要求を送ってから最初のトークンが届くまで（入力処理と順番待ちを含む）
  - 生成速度：最初のトークンから最後のトークンまでの，1秒あたりのトークン数
  - 全体の生成量：1セット（4人分）の生成トークン数の合計を，4人全員が終わるまでの時間で割った値

起動コマンドは `docs/手順書_遅延の原因とエンジン比較_20261118.md` の2章のとおり．

## 3 結果

**表1：構成ごとの4人同時の速度（各12件）**

| 構成 | 最初の出力まで（中央値） | 生成（中央値） | 生成（最小） | 4人全員の完了（中央値） | 全体の生成量 |
|---|---|---|---|---|---|
| A：RPC で層を分ける | 14.8 秒 | 31.1 tok/s | 18.6 tok/s | 29 秒 | 54.6 tok/s |
| B：Head の GPU のみ | 7.0 秒 | 45.1 tok/s | 27.1 tok/s | 17 秒 | 91.5 tok/s |
| C：GPU ごとに別々のサーバー | 4.3 秒 | 54.4 tok/s | 30.9 tok/s | 16 秒 | 82.4 tok/s |

**表2：構成 C の内訳（どちらも2人ずつ，各6件）**

| サーバー | 生成（中央値） | 生成（最小） | 最初の出力まで（中央値） |
|---|---|---|---|
| Head の GPU（RPC なし） | 77.8 tok/s | 76.0 tok/s | 3.8 秒 |
| Worker の GPU（RPC 経由，層は分けない） | 31.6 tok/s | 30.9 tok/s | 5.0 秒 |

- 3構成とも，12件すべてが最後まで回答した．
- いずれの構成も，生成速度の最小値は 10 tok/s 以上であった（gpt-oss-20b は活性パラメータが 3.6B と小さいため）．

## 4 考察

### 4.1 遅延の主な原因は RPC の通信である

GPU を2台使う構成 A は，1台だけの構成 B より遅かった．4人全員の完了は 29 秒と 17 秒，全体の生成量は 54.6 tok/s と 91.5 tok/s であり，1台に載るモデルを RPC で2台に分けると，GPU を増やしたにもかかわらず処理能力が下がった．

構成 C の内訳では，同じ2人の条件でも，RPC を通さない Head 側が 77.8 tok/s，RPC を通す Worker 側が 31.6 tok/s と，2.5倍の差があった．2つの GPU のメモリ帯域の差（448 GB/s と 360 GB/s）だけでは2割程度の差しか説明できない．このことから，1トークンごとに 1Gbps の回線を往復する RPC の通信が，生成速度を大きく下げていると考えられる．層を分けない場合でも，RPC を通すだけで遅くなっている．

### 4.2 GPU を分け合う影響は小さい

1台の GPU で4人を受けた構成 B の1人あたりの生成速度（45.1 tok/s）は，2人を受けた構成 C の Head 側（77.8 tok/s）より低いが，全体の生成量は B が 91.5 tok/s で，人数で分け合った分だけ遅くなっていると見られる．GPU を分け合うこと自体による余分な損失は，RPC の影響に比べて小さい．

### 4.3 同時利用に向いた構成

同時利用を重視する場合は，RPC を避け，1台の GPU に載るモデルを GPU ごとに独立したサーバーで動かす構成が有利と考えられる．ただし，この構成では1台に載らないモデルは使えない．

| モデル | 容量 | Head（16GB） | Worker（20GB） | 精度（前回の調査2） |
|---|---|---|---|---|
| Gemma 4 12B | 7.1GB | 載る | 載る | 91.8%，誤検知 0 |
| gpt-oss-20b | 11.6GB | 載る | 載る | 72.1%（基準未達） |
| Gemma 4 26B-A4B | 16.9GB | 載らない | 載る | 88.5%，誤検知 0 |
| Qwen3.6-35B-A3B | 22.1GB | 載らない | 載らない | 91.8%，誤検知 0 |

Gemma 4 12B は，精度が高く，両方の GPU に載るため，独立したサーバー構成で速度の基準を満たせば，現構成で4人同時に使うモデルの有力な候補になる．

### 4.4 この実験の限界

- 各構成1セット（12件）の測定である．差は大きいため結論は変わらないと考えるが，再測定で確かめる余地がある．
- 構成 C の Worker 側は RPC を通しているため，Worker の GPU 単体の速度は測れていない．
- 入力が長く出力が短い条件（ログの要約）のみで測っている．

## 5 今後

1. **Worker の GPU 単体の速度を測る**：Worker で llama-server を直接動かし，構成 C の Worker 側と同じ2人の条件で測る（測定 D）．Head 側に近い速度が出れば，4.1 の結論が確かめられる．
2. **Gemma 4 12B を，GPU ごとに独立したサーバー（RPC なし）で4人同時に測る**（測定 E）．比較のため，現構成（RPC で層を分ける）でも同じ条件で測る（測定 A'）．
3. **エンジンの比較**：同じ Worker の GPU で，llama.cpp と vLLM を比べる（実験2）．

手順は `docs/手順書_遅延の原因とエンジン比較_20261118.md` の7章（測定 D・E・A'）と3章（実験2）．
