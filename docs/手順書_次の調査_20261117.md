## 3. RPC あり・なしの対照実験

### 3-1. 目的
「4人同時に使うと遅くなるのは、RPC で2台に分けているせいか」を確かめる。いまのデータでは、RPC のせいか、単に4人で GPU を分け合っているせいかを区別できない。

同じモデル（gpt-oss-20b。どちらの GPU にも1台で載る）を、同じ4人同時の条件で、3通りの構成で測る。

| 構成 | 内容 | label |
|---|---|---|
| A | RPC で2台の GPU に層を分ける（今の構成） | `research2-cmp-gpt-oss-20b-rpc` |
| B | Head の GPU 1台だけで4人を受ける | `research2-cmp-gpt-oss-20b-head` |
| C | GPU ごとに別々のサーバーを立て、2人ずつ受ける | `research2-cmp-gpt-oss-20b-split` |

### 3-2. デバイス名を確かめる
構成 B と C では、使う GPU を名前で指定する。まず名前を確かめる。
```bash
~/llama.cpp/build/bin/llama-server --rpc 172.18.1.57:50052 --list-devices
```
`CUDA0`（Head の A4000）と、RPC の装置（`RPC0` など）が表示される。表示された名前が `CUDA0` と `RPC0` でなければ、以下のコマンドと `models.json` の `cmp-gpt-oss-20b-head` の `--device` の値をその名前に置き換える。

### 3-3. 構成 A と B（自動）
```bash
python3 run_all.py --phases speed4 --only cmp-gpt-oss-20b-rpc,cmp-gpt-oss-20b-head
```

### 3-4. 構成 C（手で2つ起動する）
tmux の窓を3つ使う（`Ctrl-b` → `c` で増やし、`Ctrl-b` → 数字で切り替える）。

窓1：Head の GPU で動かすサーバー（ポート 8080、2人分）
```bash
~/llama.cpp/build/bin/llama-server -hf unsloth/gpt-oss-20b-GGUF:Q4_K_M --no-mmproj -ngl 99 --device CUDA0 -c 16384 -np 2 --ctx-checkpoints 0 --cache-ram 0 --host 127.0.0.1 --port 8080
```
窓2：Worker の GPU で動かすサーバー（ポート 8081、2人分）。API は Head で受け、計算は RPC で Worker の GPU に任せる。層は分けない。
```bash
~/llama.cpp/build/bin/llama-server -hf unsloth/gpt-oss-20b-GGUF:Q4_K_M --no-mmproj -ngl 99 --rpc 172.18.1.57:50052 --device RPC0 -c 16384 -np 2 --ctx-checkpoints 0 --cache-ram 0 --host 127.0.0.1 --port 8081
```
2つとも `model loaded` が出たら、窓3で測る（4本を 8080 と 8081 に2本ずつ振り分ける）。
```bash
cd ~/llm_test/bench && python3 audit_bench.py out_audit/audit.log --parallel 4 --runs 3 --url http://127.0.0.1:8080 --url http://127.0.0.1:8081 --label research2-cmp-gpt-oss-20b-split
```
終わったら、窓1と窓2で `Ctrl-c` を押して止める。

- 構成 C は、Worker 側に新しくポートを開けずに済むよう、2つともサーバーを Head に置いている。Worker の GPU を使うサーバーは RPC を使うが、層を分けないので、2台を順番に通る処理はなくなる。
- 起動の確認は、`nvidia-smi`（Head）と、Worker の `nvidia-smi` で、それぞれの GPU にモデルが載っていることを見る。

### 3-5. 結果を見る
```bash
python3 report.py
```
`cmp-gpt-oss-20b-rpc`／`-head`／`-split` の3行を比べる。

### 3-6. 結果の読み方

| 結果 | 言えること |
|---|---|
| A が B・C より明らかに遅い | 4人同時の遅さには、RPC で層を分けることが効いている |
| A と B が同じくらい | 遅さの主な原因は、4人で GPU を分け合うこと。RPC の影響は小さい |
| C が最も速い | 同時利用を重視するなら、GPU ごとに独立したサーバーを立てるほうがよい |

## 5. エージェントとしての測定

### 5-1. 目的
道具を使って調べるエージェントとして使ったときの、精度・道具の使い方・速度を測る。3モデルとも UNIX 時刻の換算ができなかったが、換算の道具を渡せば解けるはず。「道具を正しく使えるか」がそのまま差として出る。

### 5-2. 何を測るか（`agent_bench.py`）
ログは丸ごと渡さない。モデルは次の道具で調べ、最後に `submit_answer` で結論を出す。

| 道具 | 内容 |
|---|---|
| `log_info` | 行数、最初と最後の行 |
| `read_lines` | 指定した範囲の行（1回 40 行まで） |
| `grep` | 正規表現で行を探す（1回 30 件まで） |
| `hex_decode` | 16進数を文字列に直す（sudo のコマンド） |
| `decode_saddr` | SOCKADDR を IP アドレスとポートに直す |
| `epoch_to_jst` | UNIX 時刻を日本時間に直す |
| `submit_answer` | 結論を提出して終わる |

1問ごとに記録するもの：点数、終わり方（提出した／本文に書いて終えた／答えなかった／手数の上限）、道具を呼んだ回数、形式の誤り、同じ呼び出しの繰り返し、かかった時間、生成速度、キャッシュから読んだ割合。

条件：
- 問題は精度の測定と同じ7本。1問を2回ずつ解かせる（エージェントは回ごとに手順が変わるため）。
- temperature 0.7、推論オフ、1回の生成の上限 2,048、1問の手数の上限 30。
- キャッシュは有効（エージェントは、前回までの入力をキャッシュから読む使い方をするため）。
- 文脈は1人あたり 32k（4人同時なら合計 128k）。
- llama-server には `--jinja` を付ける（ツール呼び出しに必要。`run_all.py` が付ける）。

### 5-3. まず1問だけ、動きを見る
道具を正しく呼べるかを、目で確かめる。Qwen3.6 の例：
```bash
~/llama.cpp/build/bin/llama-server -hf unsloth/Qwen3.6-35B-A3B-GGUF:UD-Q4_K_M --no-mmproj -ngl 99 --rpc 172.18.1.57:50052 -c 32768 -np 1 --jinja --host 127.0.0.1 --port 8080
```
別の窓で：
```bash
cd ~/llm_test/bench && python3 agent_bench.py quiz_set/inc1/audit.log --runs 1 --verbose --label try-qwen3.6b
```
`[tool] grep(...)` のように道具を呼ぶ様子が出れば動いている。道具を一度も呼ばずに終わる場合は、`--jinja` が付いているかを確かめる。終わったら llama-server を `Ctrl-c` で止める。

下のほうに「エージェント」の表が出る。見る列：

| 列 | 意味 |
|---|---|

### 5-7. うまくいかないとき

| 症状 | 対処 |
|---|---|
| 道具を一度も呼ばない（終わり方が `no_answer` や `text`） | `--jinja` が付いているか確かめる。付いていても呼ばないなら、そのモデルはツール呼び出しが苦手 |
| `agent4-` で `out of memory` | 文脈 128k が載らない。`run_all.py` の `agent4` の `-c 131072` を `65536` にしてやり直す（1人あたり 16k になる） |
| 終わり方が `step_limit` ばかり | 同じ呼び出しを繰り返している。やり取りの全文を読む。必要なら `--max-steps 40` |
| gpt-oss で回答が空 | 推論で上限を使い切っている。`agent_bench.py` に `--max-tokens 4096` を付ける（`models.json` の `bench_extra` に書く） |
