# 研究メモ（調査1・調査2）下書き

## 1 はじめに

llama.cpp[1] を用いて GPU クラスタを構築した．その一歩として，同時使用の有無でどの程度のモデルを動かすことができるのかを調査した．その結果をまとめるために，研究メモを作成する．

## 2 調査内容

### 2.1 調査項目

**調査1**　同時使用を考慮せず，現構成でどの程度のモデルを動かすことができるか

**調査2**　4人同時使用を想定して，現構成でどの程度のモデルを動かすことができるか

### 2.2 調査1で用いるモデル

表1に示すモデルについて，以下の条件を満たすかを調査する．

- GPU クラスタ上に重みを展開できるか
- 10分以内に応答を返せるか

また，次の条件を満たすものについて，回答内容の精度検証および調査2を実施する．

- トークン生成速度 10 tok/s 以上

入力には，架空の auditd ログ（67行，5.7k〜7.4k トークン）を用い，ログの要約を3回行わせた．値は3回の中央値である．

### 2.3 調査1の結果

表2に結果を示す．どのモデルも重みを展開することはできたものの，重みが総 VRAM 36GB を超えるモデルは，重みの一部をメインメモリに置くため，トークン生成速度が大幅に低下した．ただし gpt-oss-120b は，重みが約 63GB あるものの，1トークンの計算に使うパラメータ（活性パラメータ）が 5.1B と小さいため，15.0 tok/s で条件を満たした．

調査1の結果を踏まえ，調査2では次のモデルを検証する．

- Qwen3.6-35B-A3B
- GLM-4.7-Flash
- gpt-oss-120b

### 2.4 調査2の目的

4人が同時に使用した場合でも実用的な速度で動作し，かつ回答の精度が高いモデルを選ぶ．将来，エージェントや教材の基盤として用いることを想定し，現構成における最善のモデルを決めることを目的とする．

### 2.5 調査2の評価方法

調査2では，次の2点でモデルを評価する．

**速度**
- 測るもの：4人が同時に使ったときの，1人あたりのトークン生成速度
- 測り方：ログ（約7千トークン）の要約を4人同時にリクエストし，これを3セット行う（計12件）
- 合格：12件の最小値が 10 tok/s 以上

**精度**
- 測るもの：架空の auditd ログの分析の正しさ
- 測り方：ログ7本（侵害あり5本，侵害なし2本）について6問に答えさせ，回答の JSON を正解と照合する（61点満点，採点項目は表4）
- 合格：正答率 85% 以上，かつ誤検知（侵害なしのログを「侵害あり」と判定）が 0 件

両方を満たすモデルを合格とし，該当がなければ最も近いものを選ぶ．

当初の3モデルがいずれも速度の基準を満たさなかったため，より小さいモデル5つを対象に加えた（表3）．

### 2.6 調査2の結果

表5に結果を示す．速度と精度の両方を満たすモデルはなかった．

| 基準 | 満たしたモデル |
|---|---|
| 精度 | Qwen3.6-35B-A3B，Gemma 4 26B-A4B，Gemma 4 12B，gpt-oss-120b |
| 速度 | LFM2.5-24B-A2B，gpt-oss-20b（いずれも精度は再測定中※） |

- **最も基準に近い**：Gemma 4 26B-A4B（精度は合格，速度の最小値は 9.9 tok/s で基準まで 0.1 tok/s）
- **最も精度が高い**：Qwen3.6-35B-A3B と Gemma 4 12B（正答率 91.8%．ただし速度の最小値はいずれも 8.1 tok/s）

※ 回答の前に推論を出力するモデルで，推論だけで生成上限に達し，回答が打ち切られた．生成上限を大きくして再測定する．

## 3 考察

### 3.1 気が付いたこと

RPC による分散推論は，単独での使用には有効であった．1台の GPU には載らないモデル（Qwen3.6-35B-A3B は約 22GB）を，2台の GPU にまたがって動かすことができた．一方，4人同時に使用すると，全員の回答がそろうまでの時間は単独時の3〜4倍になった．今回の測定は，入力が長く（約7千トークン）出力が短い条件であり，同じセットの中でも1人あたりの生成速度は 5〜33 tok/s とばらついていた．このことから，4人同時の遅さは，他の人の入力処理と GPU を分け合ったことによる影響が大きいと考えられる．

速度は，モデルの総パラメータ数ではなく，1トークンの計算に使う活性パラメータ数と，重みの置き場所で決まっていた．gpt-oss-120b（総 117B，活性 5.1B）は条件を満たしたが，ほぼ同じ規模の Qwen3.5-122B-A10B（総 125B，活性 10B）は満たさなかった．また，密なモデルである Gemma 4 12B と Qwen3.5-9B は，容量は小さいものの，1人での生成速度は MoE の Qwen3.6-35B-A3B や gpt-oss-20b より遅かった．4人同時でも速度を保てたのは，LFM2.5（活性 2.45B）や gpt-oss-20b（活性 3.6B）のように，活性パラメータが特に小さい MoE であった．さらに，重みの一部をメインメモリに置くと，入力の処理が極端に遅くなった．GPU にすべて載るモデルは 1,500 tok/s 以上で入力を処理したが，メインメモリを使うモデルは 43〜160 tok/s にとどまった．長いログを入力する用途では，生成速度よりも入力の処理時間が問題になる．

精度については，今回の課題ではモデルの大きさにあまり左右されなかった．密な 12B の Gemma 4 12B が，36B の Qwen3.6-35B-A3B と同じ 91.8% であった．失点の大半は侵入時刻の項目であり，gpt-oss-120b 以外のモデルは，UNIX 時刻を日本時間に換算する問題に全問不正解であった．存在しない日付を答えるモデルもあった．また，誤検知の出方はモデルによって異なり，GLM-4.7-Flash，Qwen3.5-9B，gpt-oss-20b は，侵害のないログに含まれる，インターネットからの無差別な総当たりや社内からの正規のログインを攻撃と判定した．

推論を出力するモデルは，回答までに時間がかかった．LFM2.5 は，1問に 73 秒かけても推論が終わらず，回答に至らなかった．調査1の MiniMax-M2.7 も，3回とも推論だけで生成上限に達し，回答が空であった（表2の応答時間は打ち切りまでの時間である）．

### 3.2 疑問に思ったこと

第一に，4人同時の遅さが RPC によるものかは，今回のデータでは判断できない．4人で1つの GPU を分け合えば，RPC を使わなくても遅くなるためである．RPC で層を2台に分ける構成と，1台の GPU のみを使う構成，GPU ごとに独立したサーバーを立てる構成とを比較する必要がある．

第二に，エージェントとして使った場合にも，同じ順位になるかはわからない．今回はログを丸ごと渡し，1回で答えさせた．エージェントは道具（検索や変換など）を何度も呼び出し，前回までの入力をキャッシュから読むため，速度と精度のどちらも今回と異なる可能性がある．特に，時刻の換算は道具を使えば解けるはずであり，道具を正しく使えるかどうかが精度の差になると考えられる．

第三に，測定条件が十分かという点である．精度の問題は，1種類の侵害の筋を変形した7本で，各1回しか解かせていないため，数点の差は誤差の範囲である．また，速度の最小値は試行回数が増えるほど小さくなりやすいため，基準の定め方を検討する必要がある．Gemma 4 26B-A4B の 9.9 tok/s と基準との差（0.1 tok/s）も，測定のばらつきより小さい．

第四に，推論を出力するモデルをどう評価するかである．生成上限を十分に大きくすれば精度は測定できるが，その分，回答までの時間は長くなる．教材やエージェントで使う場合に，どこまでの待ち時間を許容するかを決める必要がある．

## 4 まとめ

現構成で，同時使用の有無によって動かせるモデルの規模を調査した．単独での使用では，6モデルすべてを展開でき，3モデルが 10 tok/s 以上で動作した．4人同時の使用では，速度と精度の両方を満たすモデルはなく，最も近いのは Gemma 4 26B-A4B であった．速度は重みが GPU に載り切るかで大きく変わり，同時使用時は入力処理と生成で GPU を取り合うことで速度がばらついたと考えられる．RPC による分散推論は大きなモデルを単独で動かすには有効だが，同時使用では別の構成のほうが有利な可能性がある．また，今回の結果は短い文脈で1回答えさせた場合のものであり，エージェントとして使う場合は変わると考えられる．今後は，再測定と構成の比較を行い，エージェントとしての評価を経て教材の対象とするモデルを決める．
