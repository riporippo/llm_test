## 2. 調査2に進めるモデル

研究メモの基準（生成 10 tok/s 以上）を満たすのは次の3つ。

1. **Qwen3.6-35B-A3B**
2. **GLM-4.7-Flash**
3. **gpt-oss-120b**

- 上の2つは2台の GPU にすべて載っていて、入力処理も生成も桁違いに速い。4人同時でも余裕がある見込み。
- **gpt-oss-120b は境目にいる。** 3回目は 10.0 tok/s まで落ちた。専門家層をメインメモリに置く構成は、同時に使う人数が増えると1人あたりの速度が大きく下がりやすいので、調査2では 10 tok/s を割る可能性が高い。「100B 級が4人同時で使えるか」を確かめる1点として残す価値はある。

## 3. 注意が要る点

### 3.1 MiniMax-M2.7 は回答が空だった
3回とも、生成が上限の 1,024 トークンちょうどで止まり、回答（content）は空だった。推論（thinking）だけで上限を使い切ったと考えられる。
- 生成速度（4.0 tok/s）と入力処理速度は有効。
- 「10分以内に出力を返せるか」は、このデータでは判定できない。推論のあとに回答を書くので、実際の所要時間は 364 秒より長くなる。4.0 tok/s だと、10分（入力処理の約2分を除く約8分）で書けるのは約1,900 トークンまで。
- 判定したい場合は、`--max-tokens 4096` で測り直す。10 tok/s には届かないので、調査2の選定には影響しない。

### 3.2 gpt-oss-120b は表2と違う量子化で測っている
研究メモの表2は `ggml-org/gpt-oss-120b-GGUF`（MXFP4、63GB）だが、測定は `unsloth/gpt-oss-120b-GGUF:Q4_K_M`。メモの表か測定のどちらかを合わせる。

### 3.3 起動時の設定（`command.txt` より）
共通：`--no-mmproj -c 8192 -np 1 --rpc 172.18.1.57:50052 --host 127.0.0.1 --port 8080 --ctx-checkpoints 0 --cache-ram 0`（gpt-oss-120b だけ `--no-mmproj` なし）

| モデル | 追加のオプション | 重みの配分 |
|---|---|---|
| Qwen3.6-35B-A3B、GLM-4.7-Flash | `-ngl 99` | 全層を2台の GPU に載せる |
| gpt-oss-120b、Qwen3.5-122B、MiniMax-M2.7、Qwen3.5-397B | `-t 8`（`-ngl` と `--n-cpu-moe` は指定なし） | llama.cpp の自動配分 |

- 大きい4モデルは自動配分なので、GPU・Worker・メインメモリに何 GB ずつ載ったかは起動ログを見ないとわからない。`run_all.py` で測ると、`logs/run_all_<日時>.csv` に配分が残る。
- Qwen3.5-122B は 6.4 tok/s で、見込みの 10〜15 tok/s より遅い。自動配分の結果を見て、手で詰める余地があるかを確かめたい。

### 3.4 生成が短い
システムプロンプトが「数文で要約」なので、生成は 67〜182 トークンしかないモデルが多い（gpt-oss-120b だけ 515〜831）。3回の値はよく揃っているので速度の値としては使えるが、長い回答での速度は別に確かめたほうがよい。

## 5. 調査2のやり方

`audit_bench.py` に `--parallel` を追加した。同じログを4本同時に投げ、1人あたりの速度と、4人全員が終わるまでの時間を記録する。

llama-server は、同時に受ける本数と文脈長を4人分にして起動する（`-c` は全員の合計なので 8192 × 4）。
```bash
./build/bin/llama-server -hf unsloth/Qwen3.6-35B-A3B-GGUF:UD-Q4_K_M --no-mmproj -c 32768 -np 4 --rpc 172.18.1.57:50052 --host 127.0.0.1 --port 8080 --ctx-checkpoints 0 --cache-ram 0
```
```bash
python3 audit_bench.py out_audit/audit.log --parallel 4 --label research2-qwen3.6
```

- 文脈が4倍になるぶん、KV キャッシュが GPU のメモリを多く使う。調査1でぎりぎり載っていたモデルは、載る層が減って遅くなることがある。gpt-oss-120b は `--n-cpu-moe` の調整（または自動配分）をやり直す。
- 判定の基準（1人あたり何 tok/s 以上、何秒以内）を、測る前に研究メモで決めておく。
- 連続稼働試験で止まった原因が Worker のスリープだった場合に備え、Worker のスリープは切っておく。
