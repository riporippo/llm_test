# 手順書：4人同時の遅さの原因と、ほかのエンジンでの比較

作成：2026-11-18
エージェントとしての評価は、この手順書の結果を見てから考える。

## 0. この手順書で確かめること

調査2で、4人同時に使うと1人あたりの生成速度が落ち、応答時間が単独時の3〜4倍になった。この原因として、次の3つが考えられるが、今のデータでは区別できない。

| 原因の候補 | 確かめ方 |
|---|---|
| (a) RPC で層を2台に分けていること | 実験1：llama.cpp のまま、RPC を使う構成と使わない構成を比べる |
| (b) 4人で1つの GPU を分け合うこと | 実験1：GPU ごとに別々のサーバーを立て、2人ずつ受ける構成と比べる |
| (c) llama.cpp の同時処理の仕組み | 実験2・3：同じ GPU・同じモデルで、vLLM（多人数向けのエンジン）と比べる |

### 実験の一覧

| 実験 | 内容 | モデル | 場所 | 所要時間の目安 |
|---|---|---|---|---|
| 1 | llama.cpp の構成比較（RPC あり・なし・GPU ごと） | gpt-oss-20b | Head | 約1時間 |
| 2 | エンジン比較（1台の GPU）：llama.cpp と vLLM | gpt-oss-20b | Worker | 約2時間（vLLM の導入を含む） |
| 3 | エンジン比較（2台の GPU）：llama.cpp の RPC と vLLM の2台構成 | Qwen3.6-35B-A3B | Head と Worker | 半日（うまくいかない可能性あり） |

### 比べ方をそろえるための約束

- **モデルは gpt-oss-20b にそろえる**（実験1・2）。どちらの GPU にも1台で載り、vLLM でも元の形式（MXFP4）のまま動く。llama.cpp でも、元と同じ MXFP4 の GGUF（`ggml-org/gpt-oss-20b-GGUF`）を使い、量子化の違いが入らないようにする。
- **測り方はすべて `--client-timing` にそろえる**。vLLM は llama.cpp のような速度の内訳（timings）を返さないため、応答をストリーミングで受けながら、手元で時刻を計る。llama.cpp も同じ方式で測る。
  - 最初の出力まで：要求を送ってから最初のトークンが届くまで（入力の処理と、順番待ちを含む）
  - 生成速度：最初のトークンから最後のトークンまでの、1秒あたりのトークン数
- **条件は調査2と同じ**：調査1・2と同じログ（`out_audit/audit.log`、約6千トークン）の要約を4人同時に3セット（計12件）。temperature 0.7、生成上限 1,024。
- **キャッシュは切る**。4人が同じログを送るので、キャッシュが効くと入力処理を省けて、実力より速く見える。llama.cpp は `--cache-ram 0`（と要求の `cache_prompt: false`）、vLLM は `--no-enable-prefix-caching` を付ける。
- **記録の名前（label）は `cmp-` で始める**。`python3 report.py` の「構成・エンジンの比較」の表にまとめて出る。

## 2. 実験1：llama.cpp の構成比較（RPC の影響）

### 2-1. 比べる構成

| 構成 | 内容 | label |
|---|---|---|
| A | RPC で2台の GPU に層を分ける（今の構成） | `cmp-A-rpc-gpt-oss-20b` |
| B | Head の GPU（A4000）1台だけで4人を受ける | `cmp-B-head-gpt-oss-20b` |
| C | GPU ごとに別々のサーバーを立て、2人ずつ受ける | `cmp-C-split-gpt-oss-20b` |

### 2-2. デバイス名を確かめる
```bash
~/llama.cpp/build/bin/llama-server --rpc 172.18.1.57:50052 --list-devices
```
Head の GPU（`CUDA0`）と、RPC の装置（`RPC0` など）が表示される。以下のコマンドの `CUDA0`・`RPC0` は、表示された名前に置き換える。

Worker の rpc-server は、これまでどおり起動しておく（Worker の WSL）。
```bash
cd ~/llama.cpp && CUDA_VISIBLE_DEVICES=0 ./build/bin/ggml-rpc-server --host 172.18.1.57 -p 50052 -c
```

### 2-3. 構成 A：RPC で2台に分ける
窓1（Head）：
```bash
~/llama.cpp/build/bin/llama-server -hf ggml-org/gpt-oss-20b-GGUF --no-mmproj -ngl 99 --rpc 172.18.1.57:50052 -c 32768 -np 4 --ctx-checkpoints 0 --cache-ram 0 --host 127.0.0.1 --port 8080
```
窓2（Head）：
```bash
cd ~/llm_test/bench && python3 audit_bench.py out_audit/audit.log --parallel 4 --runs 3 --client-timing --label cmp-A-rpc-gpt-oss-20b
```
終わったら窓1で `Ctrl-c`。

### 2-4. 構成 B：Head の GPU だけ
窓1：
```bash
~/llama.cpp/build/bin/llama-server -hf ggml-org/gpt-oss-20b-GGUF --no-mmproj -ngl 99 --device CUDA0 -c 32768 -np 4 --ctx-checkpoints 0 --cache-ram 0 --host 127.0.0.1 --port 8080
```
窓2：
```bash
python3 audit_bench.py out_audit/audit.log --parallel 4 --runs 3 --client-timing --label cmp-B-head-gpt-oss-20b
```
起動ログに RPC の装置が出てこないこと、Worker の GPU にモデルが載っていないこと（Worker で `nvidia-smi`）を確かめる。

### 2-5. 構成 C：GPU ごとに別々のサーバー
2つとも Head で起動する。Worker の GPU を使うサーバーは RPC 経由になるが、層は分けない（Worker の GPU だけで計算する）。Worker に新しくポートを開けずに済む。

窓1（Head の GPU、ポート 8080、2人分）：
```bash
~/llama.cpp/build/bin/llama-server -hf ggml-org/gpt-oss-20b-GGUF --no-mmproj -ngl 99 --device CUDA0 -c 16384 -np 2 --ctx-checkpoints 0 --cache-ram 0 --host 127.0.0.1 --port 8080
```
窓2（Worker の GPU、ポート 8081、2人分）：
```bash
~/llama.cpp/build/bin/llama-server -hf ggml-org/gpt-oss-20b-GGUF --no-mmproj -ngl 99 --rpc 172.18.1.57:50052 --device RPC0 -c 16384 -np 2 --ctx-checkpoints 0 --cache-ram 0 --host 127.0.0.1 --port 8081
```
窓3（4本を 8080 と 8081 に2本ずつ振り分ける）：
```bash
cd ~/llm_test/bench && python3 audit_bench.py out_audit/audit.log --parallel 4 --runs 3 --client-timing --url http://127.0.0.1:8080 --url http://127.0.0.1:8081 --label cmp-C-split-gpt-oss-20b
```

### 2-6. 結果の読み方
```bash
python3 report.py
```
「構成・エンジンの比較」の表で、A・B・C の3行を比べる。

| 結果 | 言えること |
|---|---|
| A が B より明らかに遅い | 4人同時の遅さには、RPC で層を分けることが効いている（原因 a） |
| A と B が同じくらい | RPC の影響は小さく、4人で GPU を分け合うことが主な原因（原因 b） |
| C が最も速い | 同時利用では、GPU ごとに独立したサーバーを立てるほうがよい |

## 3. 実験2：エンジン比較（1台の GPU）

同じ Worker の GPU（RTX 4000 Ada 20GB）、同じモデル（gpt-oss-20b、MXFP4）で、llama.cpp と vLLM を比べる。測定も Worker の中から行う。

| エンジン | label |
|---|---|
| llama.cpp | `cmp-eng-llamacpp-worker-gpt-oss-20b` |
| vLLM | `cmp-eng-vllm-worker-gpt-oss-20b` |
| SGLang（任意） | `cmp-eng-sglang-worker-gpt-oss-20b` |

**注意**：Worker の rpc-server は止めておく（同じ GPU を使うため）。rpc-server の窓で `Ctrl-c`。

### 3-1. llama.cpp（Worker の WSL）
窓1：
```bash
cd ~/llama.cpp && ./build/bin/llama-server -hf ggml-org/gpt-oss-20b-GGUF --no-mmproj -ngl 99 -c 32768 -np 4 --ctx-checkpoints 0 --cache-ram 0 --host 127.0.0.1 --port 8080
```
窓2：
```bash
cd ~/llm_test/bench && python3 audit_bench.py out_audit/audit.log --parallel 4 --runs 3 --client-timing --label cmp-eng-llamacpp-worker-gpt-oss-20b
```
終わったら窓1で `Ctrl-c`。

### 3-2. vLLM を入れる（Worker の WSL、初回だけ）
専用の仮想環境に入れる（数 GB のダウンロードがある）。
```bash
python3 -m venv ~/vllm-env && source ~/vllm-env/bin/activate && pip install -U pip && pip install vllm
```
入ったことと、版を確かめる（研究メモに記録する）。
```bash
python3 -c "import vllm, torch; print(vllm.__version__, torch.__version__, torch.cuda.is_available(), torch.cuda.get_device_name(0))"
```
`True` と `NVIDIA RTX 4000 Ada Generation` が出ればよい。

### 3-3. vLLM で測る（Worker の WSL）
窓1（仮想環境に入ってから）：
```bash
source ~/vllm-env/bin/activate && vllm serve openai/gpt-oss-20b --host 127.0.0.1 --port 8000 --max-model-len 8192 --max-num-seqs 4 --gpu-memory-utilization 0.90 --no-enable-prefix-caching
```
- `--max-model-len 8192`：1人あたりの文脈長（llama.cpp の `-c 32768 -np 4` と同じく、1人 8k）
- `--max-num-seqs 4`：同時に処理する数（llama.cpp の `-np 4` にあたる）
- `--no-enable-prefix-caching`：キャッシュを切る（4人が同じログを送るため）

`Application startup complete` が出たら、窓2で測る（URL が 8000 番であることに注意）。
```bash
cd ~/llm_test/bench && python3 audit_bench.py out_audit/audit.log --parallel 4 --runs 3 --client-timing --url http://127.0.0.1:8000 --label cmp-eng-vllm-worker-gpt-oss-20b
```
終わったら窓1で `Ctrl-c`。

### 3-4. （任意）SGLang でも測る
```bash
python3 -m venv ~/sglang-env && source ~/sglang-env/bin/activate && pip install -U pip && pip install "sglang[all]"
```
```bash
source ~/sglang-env/bin/activate && python -m sglang.launch_server --model-path openai/gpt-oss-20b --host 127.0.0.1 --port 8000 --context-length 8192 --max-running-requests 4 --disable-radix-cache
```
```bash
python3 audit_bench.py out_audit/audit.log --parallel 4 --runs 3 --client-timing --url http://127.0.0.1:8000 --label cmp-eng-sglang-worker-gpt-oss-20b
```

### 3-5. 結果を Head にまとめる
Worker で測った結果（`bench/audit_bench_results.csv`）を push し、Head で pull してから `report.py` を実行する。
```bash
cd ~/llm_test && git add bench/audit_bench_results.csv && git commit -m "エンジン比較（Worker）" && git push
```
Head と Worker の両方で CSV に追記していると、push や pull のときに衝突する。片方で測っている間は、もう片方で測らないようにする。

### 3-6. 結果の読み方

| 結果 | 言えること |
|---|---|
| vLLM が llama.cpp より明らかに速い（特に「生成 最小」と「全員完了」） | 4人同時の遅さには、llama.cpp の同時処理の仕組みが効いている（原因 c） |
| 同じくらい | 4人程度では、エンジンの違いは小さい |

1人で使う場合の差も見たいときは、`--parallel 1 --runs 3` で同じように測る（label は `cmp-eng-...-single`）。

## 4. 実験3：エンジン比較（2台の GPU）

1台に載らない Qwen3.6-35B-A3B を、llama.cpp の RPC と、vLLM の2台構成（層を2台に分ける方式。Ray という仕組みで2台をつなぐ）で比べる。**設定が難しく、WSL2 で動いた例は調べた範囲では見つからなかった。実験1・2の結果を見てから、必要ならやる。**

### 4-1. llama.cpp の RPC（Head）
窓1：
```bash
~/llama.cpp/build/bin/llama-server -hf unsloth/Qwen3.6-35B-A3B-GGUF:UD-Q4_K_M --no-mmproj -ngl 99 --rpc 172.18.1.57:50052 -c 32768 -np 4 --ctx-checkpoints 0 --cache-ram 0 --host 127.0.0.1 --port 8080
```
窓2：
```bash
cd ~/llm_test/bench && python3 audit_bench.py out_audit/audit.log --parallel 4 --runs 3 --client-timing --label cmp-2node-llamacpp-qwen3.6
```

### 4-2. vLLM の2台構成（準備）
- **Head（Ubuntu）にも vLLM を入れる**。Head と Worker で、Python・vLLM・Ray の版をそろえる（3-2 と同じコマンド。版がずれると動かない）。
- **2台の間で通信を許可する**。Ray と vLLM は多くのポートを使う。Head（ufw）と Worker（Hyper-V ファイアウォール）で、**相手の IP からの通信だけ**を許可する。Ray には認証がないので、測定が終わったら規則を元に戻す。
- **使うネットワークを指定する**（両方の台で、自分の IP を入れる）。
  ```bash
  export VLLM_HOST_IP=<自分のIP> NCCL_SOCKET_IFNAME=<LANのインターフェース名> GLOO_SOCKET_IFNAME=<LANのインターフェース名>
  ```
  インターフェース名は `ip -4 addr` で、自分の IP が付いている名前（例：`eno1`、`eth0`）。
- **モデルを両方の台に置く**（それぞれでダウンロードされる）。

### 4-3. vLLM の2台構成（起動と測定）
Head：
```bash
source ~/vllm-env/bin/activate && ray start --head --node-ip-address=<HeadのIP> --port=6379
```
Worker（WSL）：
```bash
source ~/vllm-env/bin/activate && ray start --address=<HeadのIP>:6379 --node-ip-address=172.18.1.57
```
Head で、2台の GPU が見えていることを確かめる（GPU が 2 と出ればよい）。
```bash
ray status
```
Head で起動する：
```bash
vllm serve cyankiwi/Qwen3.6-35B-A3B-AWQ-4bit --host 127.0.0.1 --port 8000 --pipeline-parallel-size 2 --tensor-parallel-size 1 --distributed-executor-backend ray --max-model-len 8192 --max-num-seqs 4 --gpu-memory-utilization 0.90 --no-enable-prefix-caching
```
測る：
```bash
cd ~/llm_test/bench && python3 audit_bench.py out_audit/audit.log --parallel 4 --runs 3 --client-timing --url http://127.0.0.1:8000 --label cmp-2node-vllm-qwen3.6
```
終わったら、両方の台で Ray を止める。
```bash
ray stop
```

| 列 | 意味 |

- 各構成・エンジンの起動コマンド（この手順書のとおりなら、そう書けばよい）

### 結論の組み立て方

| 実験1 | 実験2 | 結論 |
|---|---|---|
| A ≒ B、C が速い | vLLM ≒ llama.cpp | 原因は GPU の分け合い。GPU ごとに独立したサーバーにすればよい |
| A ≒ B | vLLM が速い | 原因はエンジン。同時利用には vLLM などを使う |
| A が遅い | ― | RPC の影響がある。同時利用では RPC を避ける |

## 6. うまくいかないとき

| 症状 | 対処 |
|---|---|
| `--device` で「unknown device」 | 2-2 の `--list-devices` で表示された名前を使う |
| 構成 B・C で、Head の GPU（16GB）に載らない | `-c` を半分にする（B は `-c 16384 -np 4`、C は `-c 8192 -np 2`）。1人あたりの文脈が 4k になるので、その旨を記録する |
| vLLM の起動で「CUDA out of memory」 | `--gpu-memory-utilization` を 0.85 に下げる。だめなら `--max-model-len 6144` |
| vLLM で gpt-oss が動かない（対応していない GPU と言われる） | vLLM を最新にする。それでもだめなら、実験2は Gemma 4 26B-A4B（llama.cpp は `unsloth/gemma-4-26B-A4B-it-GGUF:UD-Q4_K_M`、vLLM は `cyankiwi/gemma-4-26B-A4B-it-AWQ-4bit`）で行う。ただし量子化の方式が違うことを記録する |
| `audit_bench.py` が vLLM で「Health check failed」 | URL のポート（8000）を確かめる。起動の途中（モデルの読み込み中）は失敗するので、`Application startup complete` を待つ |
| Ray で Worker が参加できない | 2台の間の通信がファイアウォールで止められていないか、`VLLM_HOST_IP` などが正しいかを確かめる。WSL2 のミラーモードでは、Hyper-V ファイアウォールの規則が効く |
| Worker の CSV と Head の CSV が衝突した | 片方の CSV を別名で保存しておき、pull したあとに行を足し直す |
